# Admin v6 instruction-history projection proposal

The existing `admin-action` receipt is authoritative for its gateway action, but it does not persist a versioned v6 action kind or a canonical place membership for arbitrary actions. Its `subject` can be an intent ID or a work-card ID. `decision.record` therefore cannot be joined to a place by matching `subject` to a scope key; `expansion.scope.set` cannot be labeled a new hunt without knowing whether it continued an existing instruction. The partial `admin-v6/history@1` adapter exposes only global runner pause/resume receipts. It must remain unannounced by live pulse and its `page.total` remains unknown.

Gateway receipts live in the dedicated control-plane database at `cp_log_admin_receipts`, whose schema is owned by `lib/control-plane/repository/pg-schema.ts`, outside serving Drizzle migrations. The [staged control-plane SQL](migration-proposals/admin-action-history-cp-v14.sql) is **not registered or applied**. It includes deferred receipt/companion parity and immutability guards that would reject the current generic gateway append. Its tables are not safe for live reads until the receipt append and companion append are made atomic, the control-plane bootstrap/gate and providers are updated together, historical receipts are explicitly projected or left unmapped, and a verified source-set watermark can remain valid across later appends.

## Additive durable contract, no live migration in this change

At a gateway action's successful append, store an immutable companion fact keyed by the original `ActionReceipt.receiptId`. The pure `prepareActionHistoryProjection` foundation requires the committed canonical log position and record timestamp; it is not yet connected to the gateway:

- `projectionVersion`, `gatewayReceiptId`, original `type`, `idempotencyKey`, and the original append position or immutable sequence.
- A versioned `v6ActionKind` derived from the command definition and validated input, or `null` with an explicit unmapped reason. The current pure foundation maps only the fixed global runner controls. A scope-set companion may carry a proven scope and immutable instruction receipt, but its v6 kind remains null until its start/continuation/edit meaning is durably distinguishable; it is not called `hunt-start` from receipt prose.
- `scopeRefs`: exact canonical scope key **and instruction receipt ID** for each affected instruction. For globally acting commands use `us` with a global marker. Do not infer a ZCTA from a work-card label, state, subject text, or shared scope key alone.
- `targetRef` and plain display label from validated structured input. Never parse the gateway `says` prose to reconstruct identity.
- Immutable evidence references for later lifecycle steps: work/attempt/result, promotion/version/accepted record, and public reader witness, each bound to the same instruction receipt and exact subject/version. A queued action has null application/effect refs.

The companion is derived from the original receipt and validated command boundary. It does not replace or rewrite the receipt. For a scope-set action, the saved post-action decision must bind `latestDecisionReceiptId` to the action receipt, its exact canonical key to the receipt subject, and `receiptId` to the immutable instruction. A legacy backfill may populate only rows where original validated input and canonical instruction linkage are still durably available; all other legacy rows stay explicitly unclassified. Original and later hunts sharing a geography remain separate by immutable instruction receipt. A later action receipt must never replace the original lifetime budget's instruction receipt.

Index `(scopeKey, instructionReceiptId, appendPosition, gatewayReceiptId)` and expose keyset pagination with a revision/watermark. Full scoped count is available only after the projection has an audited **set equality** receipt-ID/position marker for the underlying receipt population; count equality alone is inadequate. Even after that, an unclassified legacy row with unknown scope keeps the scoped total null. The new, unwired `appendActionReceiptWithHistoryAtomic` uses one parameterized Postgres statement to allocate the log position, append the receipt and companion/scope, and mark READY incomplete; a readback checks exact canonical contents. A timeout or failed readback never causes a blind retry. The staged SQL includes deferred parity and fail-closed append triggers, but no readiness row is created. A live gateway switch must use this path for all receipt outcomes, including refusals, and only after the control-plane schema, bootstrap/gate, file/memory conformance strategy, and historical backfill are reviewed. Only then can readiness be set and maintained atomically with later appends. Until then, return `total:null` and named missing parts. Query/page limits remain bounded, and the Admin session/host guard stays required. The projection is an index of existing authority, not a new action or publication store. No live table, trigger, migration, backfill, or production write is included here.
