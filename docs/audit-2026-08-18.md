# Independent codebase audit — 2026-08-18

External read-only audit of SeanJ22/We-The-People (pre-g15, production bf0cd7b era).
Commissioned by the author; findings dispositioned into the tracker as AUD01–AUD09.
Reproduced verbatim from the auditor's report.

Bottom line
Keep the stack. TypeScript + Next.js + MapLibre + Drizzle/Neon is the right method for this product through the November 3 election and, with targeted changes to the data-serving layer, well beyond it. I found no evidence that a language or framework migration would solve the important problems. The first things that become inefficient at scale are how meetings are searched, how geographic context is resolved, and how coverage configuration is repeated—not TypeScript itself.
I also would not interpret the ~927-module figure as a 927-module browser bundle. The repository’s build check is measuring Next file-trace cardinality (*.nft.json), which is primarily a server/deployment dependency measure. That number deserves a regression budget because this repo has already suffered a real trace explosion, but it is not evidence by itself that readers download an unhealthy amount of JavaScript.
I reviewed the GitHub source as authoritative and used CLAUDE.md / state.md in Drive to distinguish intentional constraints from accidental architecture. I changed nothing.
Proposed findings
AUD-01 — Do not migrate away from TypeScript/Next before the election
Category: Stack
Cost to adopt: small — under one session to make this the explicit architectural decision; an actual replacement would itself be large — 3+ sessions by definition, realistically much larger.
Benefit: Avoids spending 3+ engineering sessions on a migration that does not remove any of the hot paths found in this audit. It also preserves one shared type system across browser UI, API routes, ingestion adapters, schema code, tests, and operational scripts.
Evidence:
• package.json:1-120 — one Node/TS toolchain covers Next, ingestion, geometry, audits, tests, Playwright and DB tooling.
• lib/sources/types.ts:300-430 — every ingestion source conforms to the same fetch / normalize / upsert interface.
• app/page.tsx:1-8 and components/map/map-canvas.tsx:1-240 — the product's primary surface is inherently browser/React/MapLibre work.
• lib/meetings/snapshot.ts:1-120 — the data-serving seam is deliberately narrow enough to replace the backing store without changing callers.
• CLAUDE.md, source-adapter contract — adding a source is intended to add an adapter directory rather than alter shared ingest logic.
Confidence: VERIFIED
Assessment: I would not introduce Python as a second permanent ingestion platform merely because the next phase involves scraping hundreds of government websites. The existing adapter contract is already the structure you would want around a heterogeneous scraper fleet. If one future publisher genuinely requires a uniquely capable Python library, a bounded offline extraction utility could be justified then. That is very different from moving ingestion wholesale to Python.
Likewise, Next.js is not causing the national-scale problem. The relevant serving operations are currently linear scans over data. Reimplementing a linear scan in another web framework merely changes the language performing the scan.
AUD-02 — Turn the existing trace checker into a real bundle/trace budget
Category: Performance
Cost to adopt: small — under one session
Benefit: Detects recurrence of a defect that previously expanded two traces to 2,554 and 2,567 files, versus 104–195 for other routes at that time. It also prevents the operator from treating the current ~927 traced modules as if they were reader-transferred JavaScript bytes.
Evidence:
• scripts/check-build-output.mjs:1-35 — records the prior 2,554/2,567 trace explosion and 122 test files entering each trace.
• scripts/check-build-output.mjs:96-210 — currently checks for tests/ and credential-shaped values, computes the largest trace, and prints it.
• docs/state.md, opening 2026-08-17 build-output section — independently records the before/after trace failure and the fix.
• Operator-provided current figure: largest traced bundle ~927 modules.
Confidence: VERIFIED
The checker already has almost everything needed. I would add two different budgets rather than one vague "bundle size" number:
1. Server trace cardinality: manifest-by-manifest file count, preferably compared against a committed baseline or route-specific ceiling.
2. Actual client cost: emitted initial JS bytes and compressed/transfer bytes for /, separately tracking MapLibre and application chunks.
That distinction matters. A 927-file NFT trace could be perfectly fine for the browser and still be an undesirable deployment trace. Conversely, a clean 150-file server trace tells you nothing about a 500 KB client chunk.
I would not split MapLibre merely to lower a module count. The map is literally the landing product.
AUD-03 — Measure, then lazy-load only non-first-paint UI
Category: Performance
Cost to adopt: small — under one session if the measurement confirms meaningful savings
Benefit: Potentially removes the measured byte weight of infrequently opened modal/tutorial code from initial client evaluation, without delaying the map itself. Exact bytes require a production/client-bundle measurement and therefore should determine whether this row is worth implementing.
Evidence:
• app/page.tsx:1-8 — / immediately enters MapEntry.
• components/map/map-entry.tsx:1-70 — MapEntry is a root client component and statically imports OfficialModal, EntityModal, WelcomeOverlay, TutorialOverlay, multiple popup implementations, the list overlay, and the map.
• components/map/map-canvas.tsx:1-55 — MapLibre itself is statically reachable through the same first-screen graph.
Confidence: SUSPECTED
The candidate split is not the map. I would measure WelcomeOverlay, TutorialOverlay, large official/entity details and similarly rare surfaces. If together they save only a few KB compressed, leave them alone—the extra async boundaries would cost maintainability.
If they represent a material chunk, dynamically loading those surfaces is invisible to a reader until the exact moment they request them, so it satisfies the zero-behavior-change requirement in normal use.
This is deliberately conditional. There is not enough read-only evidence to claim the current client bundle is too large.
AUD-04 — Resolve the governing geography once per meetings request, not twice
Category: Performance
Cost to adopt: small — under one session
Benefit: Reduces the primary /api/meetings point-in-polygon resolution from two passes to one per request. As the feature collection grows, this removes an entire repeated spatial scan from the hot path.
Evidence:
• app/api/meetings/route.ts:95-120 — calls divisionsAt(lat, lng) before searching meetings.
• app/api/meetings/route.ts:122-140 — subsequently calls coverageAt(lat, lng, ...) for the same point.
• lib/registry/server.ts:154-165 — divisionsAt() resolves the point against the loaded feature collection.
• lib/registry/server.ts:263-282 — coverageAt() receives the full feature set and point again.
• lib/registry/server.ts:15-30 — the module itself documents the current all-geometry-in-memory approach as non-national-scale.
• CLAUDE.md § Two Data Layers — Never Join Them — geography and representative identity remain separate stores.
Confidence: VERIFIED
I would give coverageAt the already-resolved divisions, or create something like a server-only contextAtPoint() that performs geometry resolution once and derives both answers from it.
This does not violate the constitution's stores-that-never-join rule. You would not be joining behavioral data to identity or using representative rosters as geometry. You would simply stop asking the same committed geometry the same question twice in one HTTP request.
This is one of the clearest benefit-per-session wins in the audit.
AUD-05 — Index the meetings snapshot in memory before it becomes national
Category: Scale
Cost to adopt: medium — one to two sessions
Benefit: Changes the request-side candidate search from approximately O(all meetings in the national snapshot) to O(candidate bucket + returned meetings) while preserving the exact current JSON snapshot and response semantics.
Evidence:
• lib/sources/snapshot/index.ts:35-86 — snapshot fetch() intentionally ignores MeetingQuery and returns snapshot.meetings whole.
• lib/sources/snapshot/index.ts:25-45 — normalization maps across the returned rows to refresh time-derived status.
• lib/meetings/query.ts:134-230 — each request filters the returned collection repeatedly for status/time, then within() performs physical/online and distance filtering for radius rungs.
• lib/meetings/snapshot.ts:333-385 — the parsed snapshot itself is process-cached by file mtime, so JSON reparsing is not the current per-request problem.
• lib/meetings/snapshot.ts:7-30 — the module explicitly anticipates changing the backing implementation as coverage grows.
Confidence: VERIFIED
The important distinction is:
The single national snapshot file is fine right now. The request algorithm over it is what stops scaling.
The implementation I would favor before a DB cutover is deliberately boring: when the snapshot mtime changes, build one in-memory search index beside the already cached parsed object. It could use state/division plus a coarse spatial grid and time buckets. fetch(query) then selects a bounded candidate set before the existing exact haversine and temporal checks run.
That lets you preserve the current provenance, deterministic deployment, stale-but-honest fallback, snapshot diffs, and all existing correctness checks.
At four pilot zips, the current O(N) behavior is inconsequential. At a few hundred governments, it is probably still tolerable. Once the snapshot represents thousands of governments and many thousands of sittings, this is the request-path bottleneck I expect to appear before TypeScript, React, or Drizzle becomes a problem.
AUD-06 — Make “covered states” one source of truth
Category: Architecture
Cost to adopt: medium — roughly one session
Benefit: Replaces at least three independently maintained state registries with one. With 47 states remaining beyond AZ/NH/NJ, this retires on the order of 94+ redundant future edit opportunities even before counting additional state-aware scripts.
Evidence:
• lib/map/districts.ts:278-330 — hard-codes FIPS_BY_ABBR for AZ, NH and NJ and explicitly says adding a state requires another edit elsewhere.
• lib/registry/server.ts:33-45 — independently hard-codes federal plus the three state officeholder roster files.
• scripts/split-congressional.mts:30-60 — independently hard-codes the same three state FIPS/USPS mappings.
• CLAUDE.md, source-adapter/shared-path discipline — repeated answers to one structural question are contrary to the project's stated preference for one shared path.
Confidence: VERIFIED
This is the most obvious architecture duplication I found that matters specifically because of the roadmap.
Create one tiny canonical build-time coverage manifest—state FIPS, USPS code, perhaps whatever generated artifacts are expected—and derive these lists from it. Keep client-safe and server-only projections separate if necessary so it doesn't accidentally enlarge the browser graph.
Today, forgetting one of three files is easy to catch with three states. At 50 states it becomes the kind of omission an AI session can make while believing the state is fully onboarded.
The adapter fleet itself is not showing the same structural problem. Its common interface is already centralized.
AUD-07 — Do not run the full test suite on a scheduled refresh that produced no data diff
Category: DevLoop
Cost to adopt: small — under one session
Benefit: The meetings workflow runs four times per day. On any no-change run, an early diff check can eliminate one complete test-suite execution plus its test startup cost. That is up to 1,460 avoidable full-suite invocations per year if every run were unchanged; actual savings depend on how often refreshes are no-ops.
Evidence:
• .github/workflows/refresh-meetings-snapshot.yml:23-31 — schedule is every six hours.
• .github/workflows/refresh-meetings-snapshot.yml:55-77 — runs ingest, then the full pnpm test, and only afterwards checks whether the snapshot changed.
• .github/workflows/refresh-dotgov-snapshot.yml:55-75 — same order exists in the weekly dotgov refresh.
• .github/workflows/refresh-meetings-snapshot.yml:1-20 — the workflow documentation explicitly recognizes “nothing changed” as a legitimate state.
• docs/state.md § Running it currently records 371 `node --test` tests on 2026-08-18. Your audit prompt says ~950; because I did not execute the suite read-only, I am treating those as two differently timed/scope-defined claims rather than silently choosing one.
Confidence: VERIFIED
The safe ordering is:
refresh → detect whether governed artifact changed → if unchanged, exit → if changed, run full existing gate → commit
That weakens nothing. Changed data still gets the exact same validation discipline. No-op jobs stop proving the same code against the same artifact every six hours.
I would not replace the full changed-data gate with a tiny targeted test merely to save CI time. That would cut against the constitution's evidence discipline. The early no-diff exit gets much of the benefit without that tradeoff.
AUD-08 — Add a spatial access path when meetings actually move to Postgres
Category: Scale
Cost to adopt: medium — one to two sessions when the DB becomes the serving path
Benefit: Prevents future viewport/radius lookups from degenerating into a table scan over a national meetings table.
Evidence:
• lib/db/schema.ts:38-145 — meetings stores latitude and longitude as independent doublePrecision columns.
• lib/db/schema.ts:112-145 — current indexes are on ocdId and startsAt; there is no spatial/geohash candidate index in this schema.
• lib/sources/types.ts:250-290 — the public query contract is explicitly latitude/longitude/radius based.
• lib/meetings/query.ts:130-235 — the serving semantics rely on arbitrary radius searches, including reader-panned viewports.
• lib/meetings/snapshot.ts:7-30 — current production serving remains snapshot-backed.
Confidence: SUSPECTED
I am not calling this a missing-index defect today, because those DB rows are not the production meetings read path.
It becomes relevant at the moment the snapshot is replaced by Postgres. At that point, either PostGIS/geography, a geohash/grid candidate column, or another bounded spatial lookup is necessary. The existing ocd_id and starts_at indexes are useful but cannot efficiently answer an arbitrary radius centered on a freely panned point by themselves.
Do it as part of the backing-store cutover, not now. Prematurely installing PostGIS before it serves a query would be architecture theater.
AUD-09 — Keep the state-focus implementation; add a performance budget to its existing measurement harness
Category: Performance
Cost to adopt: small — under one session
Benefit: Converts an unmeasured rendering-risk area into a regression budget—e.g. projection point count and frame duration at representative continental/metro/local zooms—without replacing an implementation that already contains several deliberate cost controls.
Evidence:
• components/map/state-focus-overlay.tsx:1-65 — documents one projection pass per animation frame and identifies backdrop-filter as the expensive half.
• components/map/state-focus-overlay.tsx:185-255 — clips projected rings to the visible padded box before simplifying them.
• components/map/state-focus-overlay.tsx:280-330 — coalesces redraws through requestAnimationFrame.
• components/map/state-focus-overlay.tsx:330-430 — bounds SVG filter regions rather than using effectively unbounded surfaces.
• components/map/map-canvas.tsx:78-100 — overlay is suspended when a competing full-screen filtered overlay is open because that cost was measured.
• components/map/map-canvas.tsx:520-900 — existing read-only projection/camera probes support measurement tooling.
• lib/map/state-focus.ts:1-70 — screen-space simplification exists specifically to suppress unnecessary continental-scale vertices.
Confidence: SUSPECTED
I found no architectural reason to replace this effect. In fact, it has already been optimized in the places I would first inspect: RAF coalescing, viewport clipping, post-projection simplification, finite GPU filter regions and avoiding stacked backdrop filters.
What I cannot tell read-only is whether a specific machine is spending 2 ms or 18 ms on a frame during a pinch. That is why the right next move is measurement, not another rendering rewrite.
I have deliberately not re-litigated the known zoomed-out pin-flash issue.
What I would not change
Several parts survived the audit specifically because they are already the better method.
The per-state district geometry design is right. Congressional geometry was previously one 1.63 MB national file; the current loader uses state splits, with the repo copy of Arizona around 24 KB, New Hampshire around 7 KB and New Jersey around 16 KB. The loader caches by district type and active state, removes old-state layers, and refuses stale async responses after state/style changes. lib/map/districts.ts:90-125, 278-370; public/geo/cd119-*.geojson; scripts/split-congressional.mts:1-90.
The meetings snapshot is also right for the current scale. It is parsed once per process and cached until the mtime changes. It preserves a last-known-good artifact if vendors fail, makes provenance inspectable in git, and keeps vendor traffic away from page requests. The future problem is not “JSON file bad”; it is the eventual number of records every query walks. lib/meetings/snapshot.ts:1-30, 333-385.
The source adapter abstraction is already national-scale-shaped. I would keep the contract and add adapters, not invent an ingestion framework above it. lib/sources/types.ts:300-430; CLAUDE.md, adapter contract.
The ship-time clean production build should remain expensive. scripts/handoff.mjs deliberately clears incremental build state and runs the same build Netlify runs before shipping. For an AI-session workflow, that is insurance, not wasted time. Optimize repetition before the ship gate; don't turn the final proof into a partial proof. scripts/handoff.mjs:1-90.
And I would not remove the committed national congressional source file merely to save repository/deploy disk bytes. The code explicitly retains it as the derivation/provenance input. Moving it out of public/ could technically change an existing public asset URL, violating this audit's zero-behavior-change rule. scripts/split-congressional.mts:1-35.
Scale breakpoints
At ~100 zip codes
I would expect no fundamental serving crisis. The snapshot scans and in-memory polygon resolution remain inexpensive enough at that size unless the meeting count per government becomes unusually large.
The greater risk is operational onboarding drift: another state gets a geometry split but not a roster entry, or vice versa. That is why AUD-06 is worth doing before the state count starts moving quickly.
At ~4,000 zip codes / substantial multi-state coverage
The first server inefficiencies become architectural rather than theoretical:
• repeated spatial resolution in /api/meetings;
• whole-snapshot status/time/radius scanning on every request;
• larger in-memory government geometry.
AUD-04 and AUD-05 push those limits out substantially without changing storage or UI.
At national coverage
The repository itself already calls the current registry loader untenable for the 90,837-local-government target and identifies a PMTiles/database seam. lib/registry/server.ts:15-30.
At that point I agree with the repo's direction: change the backing data structure, not the application language. Keep normalized TS contracts above it. Put spatially addressable government geometry and meeting candidates behind the narrow server APIs. The UI should barely notice.
Summary of proposed AUD rows
Direct answer to the stack question
Yes: ~92% TypeScript on Next.js is the right method for Meanwhile. The map belongs in the browser and MapLibre is a natural fit; Next gives you the client/server boundary the product already uses; TypeScript lets the same normalized civic-data contracts travel through ingestion, APIs, tests and UI; Drizzle/Neon are adequate for the persistent layer. I found no layer where changing language now produces a benefit remotely proportional to its migration cost. The meaningful architectural evolution is from linear file-backed lookup to indexed file/DB-backed lookup as the dataset grows, while leaving the TypeScript application around it intact. A wholesale framework or language migration before November 3 would spend the project's scarcest resource—AI engineering sessions—on the wrong bottleneck.
The three best benefit-per-session changes
1. Stop resolving the same geographic point twice on every meetings request — AUD-04. This is small, concrete and immediately improves the exact operation that will get more expensive as coverage expands. A non-engineer version: the server currently looks up “what governments contain this location?” twice; make it look once and reuse the answer.
2. Skip the full tests when a scheduled refresh produced no change — AUD-07. It preserves every existing safety gate on real changes and simply stops validating a nonexistent change. A non-engineer version: if the data refresh changed nothing, don't run hundreds of tests before deciding there is nothing to publish.
3. Make the list of supported states exist in one place — AUD-06. This is preventative work timed exactly for the ingestion phase. A non-engineer version: today adding a fourth state requires several separate lists to be updated correctly; before adding dozens, make one list generate the others.
AUD-05 is the next one I would queue, but I would implement it as the meeting corpus actually starts growing rather than before the ingestion volume exists.
What I could not assess read-only
• Actual current browser JS transfer bytes, compressed chunk sizes, parse/evaluation time and route-level client bundle composition. The ~927 figure is a Next trace/module count, not sufficient to answer that.
• Real MapLibre/state-focus frame times, GPU compositing cost, memory consumption and low-end-device behavior.
• Production `/api/meetings` latency distribution and how much time is currently spent in spatial resolution versus meeting filtering.
• Postgres `EXPLAIN ANALYZE` / production query timings. The meeting table is not currently the read path anyway.
• Current GitHub Actions wall-clock durations and runner-minute consumption. I inspected workflow definitions; the available read connector did not give me reliable Actions-run timing data.
• The claimed 16 allowlisted unused-variable warnings. I inspected eslint.config.mjs, tsconfig.json, and searched the repository for the obvious no-unused-vars configuration shape; I did not find a textual allowlist in those locations. Because I did not execute pnpm lint, I will not assert that the 16 do or do not exist.
• Dependency abandonment/CVE/freshness status. I stayed within the two evidence sources you authorized rather than consulting npm/GitHub upstream projects. From the repository tree itself, I did not find a compelling second framework or duplicate architectural dependency to remove.
• Every API route and every ingestion implementation line-by-line. I traced the primary map → meetings API → source → snapshot → registry path, the DB schema, build/handoff machinery, state geometry, common ingestion contract, workflows, and representative scripts. I therefore would not claim repo-wide absence of an N+1 or orphan without a full executable static-analysis pass.
One discrepancy is worth recording: the prompt describes roughly 950 tests, while the current Drive state.md records 371 `node --test` tests as of August 18, 2026. walk:all is a separate, dynamically counted production regression net. Since this was read-only, I did not manufacture a new test count by inference.
Overall judgment
The codebase is architecturally healthy for the road immediately ahead, but it is approaching the point where its intentionally small-scale data-serving assumptions need to mature. The strongest parts are unusually relevant to an AI-built system: normalized adapter contracts, explicit provenance, narrow seams around backing stores, process caching, deliberate failure semantics, testable map probes, and extensive explanations of why non-obvious code exists. That clarity has real value here and I would resist “cleanups” that merely shorten files.
The weakness is not a bad foundation. It is that pilot scope is still encoded in several places as pilot-sized data structures and lists: three-state manifests, all-geometry point resolution, and whole-snapshot meeting scans. Those are straightforward to evolve incrementally. The ingestion phase should therefore proceed on the existing stack. Before the state count accelerates, centralize coverage configuration; as the meeting corpus grows, index the snapshot candidates; and when national geometry genuinely exceeds the file-backed resolver, use the seam already built for a spatially indexed backing store. None of those requires changing what a reader sees, and none requires throwing away the architecture you already have.
