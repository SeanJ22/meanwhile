# RS-02: serve the selected state and place

RS-02 continues `04fe5ae6d` from RS-01, merges River `6b4ea17af` first, and includes BS-01 `027144fa1`. It is being verified on `stream/rs-02`. River owns integration and deployment after READY.

## Reader path

The existing Postgres store remains the authority, in AWS US East 2. Published records are selected through its state and place indexes. No runner-built reader manifest, snapshot, copied package or pointer is consulted by a reader request. Source versions and their evidence remain available for history and detail reads.

The server's resident national shelf holds Congress, its offices, the ZIP table and whatever verified President record is published. ZIP resolution needs no database query. A ZIP starts the state and local requests together. The state request uses one SQL statement for its published sources, district metadata and the selected local divisions; the local request uses one SQL statement for selected bodies, facts, calendars, rosters and publication outcomes. Both use the shared read-only WebSocket pool. Canonical payload reuse is checked against the current published version; assembled state and place answers have no cross-request memory TTL.

The ZIP state response includes the selected ZIP's coverage, rather than whole-state directories and ZIP tables. The local response keeps the information used by the map and lists, including held contact and source fields. Unopened agenda documents and other districts' directories load through the existing detail routes. A compact partial response does not mark an unopened directory as empty. Federal contact cards read offices from resident Congress data.

Agenda detail reads use the shared WebSocket connection. The calendar query resolves neighboring bodies itself and returns their registry identities; the route reuses those identities instead of downloading the state again. It loads the opened sitting's document text and versions, while retaining neighboring document URLs and meeting identities for shared-page checks. Identical inline text travels once within the SQL response and is restored to every document before composition; different extractions, empty strings and nulls remain distinct. This creates no persisted copy. Unrequested memberships, person facts and portraits are omitted from this internal agenda read. Historical recovery selects verified candidate identities before reading their payloads, rather than materializing whole old calendars. The calendar's verified merged source IDs identify a separate, request-scoped read of canonical state outcome sources.

Netlify receives durable, tagged answers for sixty seconds, with browser revalidation and no stale extension. Tags cover the state, selected places, national data and reader settings. Cache keys include the request parameters that select the answer. Existing publication paths invalidate affected tags after committing; bulk roster writes collect tags once, including changes committed before a later field fails. A failed purge is reported and expiry bounds the stale answer to one minute. Publication never waits for a reader-package build.

`lib/map/districts.ts`, `components/map/map-canvas.tsx` and `lib/map/state-focus.ts` exactly match `origin/main` at release 56 (`16679a9ea`). The district archive fallback remains `/api/boundaries/census-2025-b24d0345381f69be.pmtiles`. Release 56's existing Netlify build setting and actual live JavaScript select `https://tiles.meanwhilemaps.com/us-2025.pmtiles`; that setting is unchanged. Header, directory and tile samples from both URLs have identical SHA-256 hashes and the same 225,944,259-byte total archive length. State outlines still come from `/geo/state-outlines.geojson`. The XS-02 state-crossing prompt is unchanged. The state query returns metadata, without loading a whole-state boundary GeoJSON document.

## Production checks

Measurements use the existing production Neon endpoint and its existing `readonly` role. The checks verify the endpoint, `current_user`, read-only transactions and absence of table write grants. They suppress transfer-accounting writes and block browser writes, beacons and paid provider calls. No data publication, production purge or deployment is part of these checks.

The direct checker starts a fresh process per state. It compares the merged result with RS-01's production responses and every successful captured live response: meeting, body, seat, division, government, office and official identities, plus held contact, source, calendar, location and personal fields. It then measures repeat and next-ZIP reads. The built-browser checker starts a fresh server and guarded browser per state, with no reader API prewarming. It checks the actual rendered counts and actual boundary tiles, then exercises Tucson office cards and repeat/next-ZIP controls. Native mode maps the virtual production origin's application requests to the local build, while Chromium reads the unchanged live boundary archive over HTTP/2 through the managed network proxy. Only the isolated browser context accepts the proxy's private CA; Node's independently verified GETs establish archive byte identity. Netlify-only GETs use the live production assets. This environment has no basemap provider key, so the basemap background is outside the visual comparison.

Production contains 539 congressional records across 56 jurisdictions and 41,831 ZIP aliases. Four congressional records have no held district-office record. Production contains no verified current President record: the resident shelf agrees with the independently selected canonical sources and returns `NOT_RECORDED`. These are existing acquisition gaps; the read-only check does not manufacture or publish records. Tucson's House member and both senators do have held offices.

Actual CDN hits and tag purges for this branch require River's deployed build. Focused tests cover response headers, cache keys and invalidation after committed publications, including partial failure. Purge credentials accept production's existing `WTP_BLOBS_SITE_ID`/`WTP_BLOBS_TOKEN` and the runner's other Netlify token names. Secret reads are masked, so this work does not claim to have verified the current token's purge authorization. The production acceptance checks exercise the new built code against production data without changing the live site.

## Transport investigation

The exact older timings of 3.97 seconds in Indiana, 6.47 in California and 5.92 in Texas were not reproduced on this host. Fresh RS-01 built-browser information renders took 1.68, 1.75 and 1.80 seconds respectively. That older checker stopped at information paint and did not establish completed district paint for Indiana or California. Across fifty direct RS-01 reads, the slowest cold data read was 1.94 seconds; including module imports, the slowest was 3.73 seconds. These are different measurements from a full browser visit.

The transport problem is independently confirmed. RS-01's canonical HTTP results were uncompressed and 2.42–2.90 MB; identical WebSocket rows matched byte for byte after decoding. California took 1.12 seconds over HTTP and 0.42 seconds for the connected WebSocket query, plus 0.56 seconds to connect. The database executed those canonical statements in 14–22 ms; separate district metadata statements took 48–67 ms. These measurements do not reproduce the previously reported 4.13-second HTTP transfer or 80–177 ms database time.

Parameterized lateral lookups through the existing entity indexes restored the same complete result in 1.23 seconds. Select the place and body IDs before resolving large source payload parts, and retain parameterized index lookups when extending the query.

The first full compact-response comparison caught Houston's and Mills's held mayor seats missing. Their representatives were in the state roster but their local division metadata was absent from the selected response. The old comparison could overwrite a rich official identity with a sparse alias of that same person. The replacement compares all matching identities before declaring a held field missing.
