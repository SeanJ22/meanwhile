# ZP-01 — ZIP builds, queue coalescing, reader cache

Status: built and tested; review branch pushed without READY. The combined speed acceptance remains open pending the ZS-01 revision and deployed CDN checks.

Built on `river` f7003c318, with RIVER-PP2 929ab8524 merged first. Current River hotfixes through f6d41b4e5 are merged. No production queue, pages, schema or owner settings were changed. The additive migration applies in the production build; the normal place-page preparation fills the priorities before the runner adopts the release.

## Reader behavior

- First ZIP builds come first, largest held Census population first. Built ZIPs follow, then other places. `queued_at` and `place_id` break ties. First builds keep advancing when a large ZIP changes repeatedly.
- Publications coalesce while a page is waiting. The first arrival during an active snapshot retains one later generation and its first arrival time. A purge-only retry also becomes dirty when new data arrives. Claims use the database clock to exclude a page already built during the turn, including a page deleted from the queue and reinserted.
- HTML startup and hydrated ZIP navigation use `/api/meetings?zip=…`. State and place requests start independently. The optional JSON worker parses either response; a failed state request or worker preserves the local answer. Custom map coordinates still use their full coordinate/radius key.
- ZIP meetings carry only their ZIP and settings tags. State answers carry `reader-state-package:<state>`, national-people and settings tags. Local fact/calendar publications and local page rebuilds cannot clear state answers. Canonical non-meeting publications clear the state-package tag; national people and global owner invalidations retain their existing behavior. The optional legacy `include=state` response still carries the broad tags appropriate to its combined contents.

## Cache investigation

The reported unconditional browser bypass did not reproduce. Actual Lancaster navigation returned an expired-cache miss in 9,034 ms, then an edge hit in 221 ms. Chicago was 5,562 → 303 ms; Tucson 5,102 → 228 ms. A directly warmed Beverly Hills answer was subsequently a durable hit in actual navigation too. Requests used the same URL and `Accept: application/json`; no browser `no-store` directive was present.

The broad invalidation was real: `include=state` attached `reader-state:<state>` and national-people to the ZIP's combined answer. Local publishers clear that state tag. Separately, `/api/reader/state` carried local place-page tags despite reading canonical state inputs, so replacing a local page could clear state answers. Both links are removed from normal ZIP navigation. Tests cover preserving each answer on unrelated publication and clearing it on the publication it actually consumes.

\* Includes the small setup/queue-count transfer. These are much larger pages than the prior production workload, so its 0.2372 GB/hour is not a like-for-like savings comparison. The comparable fresh-process replay received 28,522,810 → 28,107,424 bytes, a 1.46% reduction, and throughput was 2.62% lower. There is no demonstrated throughput improvement. A much larger apparent saving from running both modes in one process was discarded because it reused already-read rows.

The sixteen random ZIPs were selected once by `ORDER BY md5(id||'ZP-01-20261026') LIMIT 16`, alongside 90210, 93535, 60601 and 85701. Their identities are in the summary. Each fresh process read the same data copy. The prior-transfer replay changes only FIFO ordering and whether the existing routing-body version is supplied; no answer fields are removed.

Two thousand repeated publications caused zero extra pending-row updates and one deferred generation during an active snapshot. The production queue had accumulated 15,077,328 updates at baseline. The new tests compare actual row tuple identities, not just generation counters.

The preparation test runs the real SQL against PostgreSQL: an existing ready ZIP receives its ordinary population priority, an unbuilt ZIP receives first-build priority, generations and held names survive, and a second preparation rewrites neither row.

A complete production-length turn (241,729 ms including finishing active builds) peaked at 802,811,904 bytes. The runner now reserves 804 MiB (measured peak plus 5%, rounded up), retaining four build leases and the 768 MiB host margin. One place-page process with four builds is admitted only with at least 1,572 MiB available; memory settings and other worker counts are otherwise unchanged. The shorter three-turn sample underestimated this reservation, so the completed-turn peak supersedes it.

## Checks and open speed acceptance

Production build, TypeScript, focused lint, the production-readonly migration gate, and focused queue, worker, reader, browser and schema tests pass. Lint reports two pre-existing unused-variable warnings in `lib/civic-data/store.ts`; no errors. The migration gate confirms all 62 established migration checksums and accepts ZP-01 as the single pending expand. Claim planning uses the new priority index with primary-key lookups for page/subject checks.

The final browser run used the production boundary URL setting and an isolated production copy. All 40 state/place responses were 200, with one place request per navigation and the intended separate tags. All 20 first meetings responses were below 3 s (maximum 2,069 ms). This is not a full-page speed pass: Beverly Hills and Lancaster took 3,323 ms and 3,444 ms until the Meetings control displayed its count. Their meetings payloads remain about 7.05 MB. The local environment has no Netlify CDN and no MapTiler key; local repeat requests cannot establish Netlify hits or the required <300 ms repeat target.
